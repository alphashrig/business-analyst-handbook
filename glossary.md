# Glossary

[🏠 Contents](README.md)

---

| Term | Meaning |
|------|---------|
| **Acceptance criteria (AC)** | Conditions a story or requirement must meet to be accepted. Often written as Given/When/Then. |
| **Agile** | An iterative approach to delivery in short cycles, with frequent feedback. Scrum and Kanban are Agile frameworks. |
| **As-is / to-be** | The current state of a process or system, and the desired future state. |
| **BABOK®** | *Business Analysis Body of Knowledge*, the IIBA's standard guide to business analysis. |
| **Backlog** | An ordered list of work items (epics, stories, defects) for a product. Owned by the Product Owner. |
| **Baseline** | An approved version of requirements or scope. Changes after this go through change control. |
| **Benefits realisation** | Measuring and managing whether a project's promised benefits actually arrive. |
| **BPMN** | *Business Process Model and Notation*, a standard notation for drawing process diagrams. |
| **BRD** | *Business Requirements Document*: business objectives, scope and requirements. |
| **Business case** | Justification for a project: problem, options, costs, benefits, risks, recommendation. |
| **Business rule** | A policy or constraint that governs business behaviour (e.g. "claims must be reported within 30 days"). |
| **Change request (CR)** | A formal request to change the baselined scope, requirements, cost or schedule. |
| **Context diagram** | A diagram showing a system and the external users and systems it interacts with. |
| **Definition of Done (DoD)** | Shared criteria for when a work item is complete. |
| **Definition of Ready (DoR)** | Shared criteria for when a story is ready to be taken into a sprint. |
| **Elicitation** | Drawing out requirements from stakeholders and other sources. |
| **Epic** | A large body of work, broken into smaller user stories. |
| **FNOL** | *First Notification of Loss*: the first report of an insurance claim (used in the QuickClaim example). |
| **FRS / SRS** | *Functional / Software Requirements Specification*: a detailed spec of system behaviour. |
| **Gap analysis** | Comparing as-is and to-be to identify what must change. |
| **Gate (stage gate)** | A decision point between phases: go, stop, or go back. |
| **Gherkin** | The *Given / When / Then* format for acceptance criteria and test scenarios. |
| **Go / no-go** | The decision meeting before deployment. |
| **Hypercare** | A period of intensive support immediately after go-live. |
| **ICT** | *Information and Communication Technology*. |
| **IIBA** | *International Institute of Business Analysis*, which publishes BABOK and offers ECBA, CCBA and CBAP. |
| **Impact analysis** | Assessing the effects of a proposed change on requirements, processes, cost, time and risk. |
| **INVEST** | Quality criteria for user stories: Independent, Negotiable, Valuable, Estimable, Small, Testable. |
| **KPI** | *Key Performance Indicator*: a measurable value showing progress toward an objective. |
| **MoSCoW** | Prioritisation: Must have, Should have, Could have, Won't have (this time). |
| **MVP** | *Minimum Viable Product*: the smallest release that delivers value and enables learning. |
| **NFR** | *Non-functional requirement*: how well the system must perform (performance, security, usability, etc.). |
| **PID / Project charter** | The document that formally authorises a project and sets its high-level scope and governance. |
| **PMO** | *Project Management Office*, a team that sets project standards and oversees the portfolio. |
| **Product Owner (PO)** | The person accountable for maximising product value and ordering the backlog. |
| **RACI** | Responsible, Accountable, Consulted, Informed: a matrix of who does what. |
| **RAID log** | Risks, Assumptions, Issues, Dependencies log, usually owned by the PM. |
| **RFP** | *Request for Proposal*: a client's formal request for vendors to bid for work. |
| **ROI** | *Return on Investment*: (benefits − costs) / costs. |
| **RTM** | *Requirements Traceability Matrix*: links requirements to objectives, design, stories and tests. |
| **Scope creep** | Uncontrolled growth in scope without matching changes to time, cost or resources. |
| **SME** | *Subject Matter Expert*: someone with deep knowledge of a business area. |
| **SMART** | Objectives that are Specific, Measurable, Achievable, Relevant, Time-bound. |
| **SoW** | *Statement of Work*: the contractual description of work an ICT vendor will deliver. |
| **SOP** | *Standard Operating Procedure*: documented steps for a business task. |
| **Sponsor** | The senior person who owns the business case, funds the project, and is accountable for its benefits. |
| **Sprint** | A fixed-length iteration (typically 1–4 weeks) in Scrum. |
| **Stakeholder** | Anyone who affects or is affected by the project. |
| **Story mapping** | Arranging user stories along a user journey to plan releases. |
| **Three Amigos** | A short discussion of a story between a BA (or PO), a developer and a tester before build. |
| **UAT** | *User Acceptance Testing*: business users confirm the solution meets their needs before go-live. |
| **Use case** | A description of how a user interacts with a system to achieve a goal, including alternate and exception flows. |
| **User story** | A short requirement in the form "As a... I want... so that...". |
| **Waterfall** | A sequential approach where phases happen once, in order. |
| **Wireframe** | A simple visual layout of a screen, without final design. |
